# 009 每日笔记与时间线（设计稿 v2）

> 状态：v1 已实现，尚未在真实 DSH 中验收。Host：`lib/schedule.js`、`lib/notes.js`；Client：`client.js` 中的 daily notes 段落；测试：`tests/notes.test.mjs`（Host 13 项）、`tests/notes-client.test.mjs`（真实 Client 对接真实 Host 路由，8 项）。第 5 节的 spike N1–N4 和第 0 节的成功标准仍待在隔离环境中验证。
>
> 与设计稿的差异：结论存在条目的 `result` 字段里，不单独建子条目；完成状态用 `state: open|done|dropped` 表示；`agentSlots` 表示每天最多派出几个 Agent 任务（设计稿里写的是"并发"）；`plan` 每次整体替换。

## 0. 为什么值得做

用 Agent 工作时，**稀缺的不是执行时间，而是你的注意力**。Agent 可以同时跑好几个，但每个都要你起个头、中途拍板、最后验收。今天这些散落在各处：想法记在别的笔记软件里，Session 列表只按时间排，结论埋在对话末尾，明天该接着做什么全靠记忆。

收件箱已经解决了"现在谁在等我"。笔记要解决的是它前后两段：

```
  记下 ──→ 派出去 ──→ 盯着 ──→ 收回结论 ──→ 排下一步
 (笔记)   (转对话)  (状态/收件箱) (自动回写)   (时间线)
    ↑                                          │
    └──────────── 每日回顾 / 顺延 ←────────────┘
```

只做前两步，就是一个能开 Session 的记事本；**闭环**才是它比 Session 列表和外部笔记软件强的地方。所以本设计的取舍都围绕一件事：**每个想法最后要么完成、要么明确放弃，不会悄悄烂在列表里。**

### 成功标准（可验证，验收时逐条核对）

| 环节 | 标准 |
|---|---|
| 记 | 打开笔记到能打字：一次点击或一个快捷键；边看对话边记时不用切走 |
| 派 | 笔记 → Session 一键完成，不离开笔记页，失败可重试 |
| 盯 | 关联 Session 的状态与原生侧栏一致（同一数据源），等你的条目自动顶到今天最上面 |
| 收 | 关联 Session 每结束一轮，结论在下一次刷新内回写到条目下方；探索的"下一步"变成可一键接受的待办 |
| 排 | 时间线区分"你的时间"和"Agent 的并发"，逾期自动顺延，拖延 3 次以上主动提醒 |
| 回顾 | 每天有一份基于真实数据的小结：完成、派出、顺延、放弃 |

默认安静：所有会花钱或会自动开 Session 的行为默认关闭、每天有上限、开启时说明代价。

## 1. 五个环节

### 1.1 记：零摩擦

| 入口 | 行为 |
|---|---|
| 侧栏「每日笔记」 | 主面板，今天的输入行自动获得焦点 |
| 右侧栏 tab（📌） | 和对话并排。**在某个 Session 旁边记下的内容，默认挂在该 Session 关联的条目下**；该 Session 没有关联条目时，记到今天 |
| 收件箱条目「记一笔」 | 把一条义务（比如 Agent 的提问）转成笔记，便于稍后再想（v1.1） |

编辑是纯大纲：单行文本、缩进、折叠，没有富文本。键盘：

| 键 | 作用 |
|---|---|
| `Enter` / `Tab` / `Shift+Tab` | 新建同级 / 缩进 / 反缩进（输入法组字时不触发） |
| `Backspace`（空行无子项） | 删除并回到上一行 |
| `↑` `↓` | 移动焦点 |
| `Mod+Enter` | 完成 / 取消完成 |
| `Mod+Shift+Enter` | 转为对话 |
| `Mod+Alt+Enter` | 先探索 |

### 1.2 派：两种起法

| 模式 | 发给 Agent 的内容 | 适合 |
|---|---|---|
| **转为对话** | 条目 + 子条目原文，相当于你自己在输入框里打字 | 已经想清楚要做什么 |
| **先探索** | 固定前缀：要求只读调研、不改文件（仅为提示，插件拿不到能强制只读的接口，实际权限仍由 DSH 审批设置决定）；要求结尾给出一个 `next-steps` 代码块，每行一条下一步，可带估时（`- 迁移配置 ~1h`） | 只有一个想法，还没想清楚怎么做 |

Workspace 的选择依次为：条目继承的 → 设置里的默认 → 最近活跃 Session 所在的 → 第一个。条目可以单独改。

执行路径（v1 在 Client 侧，全部是原生能力）：先向 Host 重读一次笔记 → `sessions.create({ workspaceId })` 新建 Session → 写入关联 → `session.prompt(..., 'queue')`；prompt 被拒绝时撤销这次关联（`unlink` 带上 sessionId，只撤销自己那一次），条目上显示原因和"重试"。

约束（2026-11-25 复审后定下）：

- **不用 `connectWorkspace`**：它会复用工作区里的空白 Session，也就是用户点"新会话"后可能写了一半草稿的那个，转换会把任务发进用户的草稿会话。
- **没有工作区就不建**：不调用不带工作区的 `sessions.create`，否则 Agent 会跑在 Host 的默认目录里。页面提示"先打开一个项目或在设置里选默认工作区"。
- **一条笔记只对应一个 Session**：已关联、已完成/放弃、建议条目都不能再转换（按钮和快捷键都一样）；排队中的转换在执行前会重新读取笔记。Host 的 `link` 遇到已关联其他 Session 的笔记直接拒绝（`ALREADY_LINKED`），所以两个标签页同时转换也不会产生第二个干活的 Agent。
- **先关联再发 prompt**：关联被拒绝时不发 prompt。此时新建的 Session 从未发过消息，在 DSH 里是隐藏的空白会话，下次"新会话"会复用它，不会堆积。
- **建议只出现一次**：每条 next-step 文本记在笔记的 `offered` 里；删掉、驳回、采纳后改写的建议，在之后的收获里都不会再冒出来。
- 关联了 Session 的笔记，清空文字后按退格不会被删掉。

### 1.3 盯：状态长在条目上

| 图标 | 含义 | 来源（全部只读，不另存） |
|---|---|---|
| ◑ 警示色 | 在等你：审批、提问、计划 | 收件箱 hard/system 义务、`pendingInteraction` |
| ◌ 旋转 | 运行中 | `sessions.list.running` |
| ● 强调色 | 跑完待验收 | `completionUnread`、review 义务 |
| ✕ 错误色 | 失败或 goal 受阻 | 收件箱 soft 义务 |
| ○ / ✓ / ⊘ | 未开始 / 完成 / Session 已删除或归档 | 笔记、列表 |

今天分组的顶部有一条**状态条**：「2 个在等你 · 3 个在跑 · 1 个待验收」，点击分别过滤。等你的条目在今天里排到最前面。点图标即打开 Session；在等你的条目，如果收件箱能原地处理（审批/提问），悬停时直接给出收件箱的动作，不用跳走。

### 1.4 收：结论回到笔记里（这是关键）

关联 Session 的一轮结束后，Host 把结果写回条目下方。写回的是一行只读子条目，带 Agent 标记：

```
◑ 极简大纲笔记插件设计
    ↳ 已完成数据层和排程，Client 待写；需要你确认自动探索的默认值   ← 结论（每轮覆盖，不累积）
    ☐ 建议：实现 Client 笔记页 ~3h                                  [接受] [忽略]
    ☐ 建议：补右侧栏 pin ~1h                                         [接受] [忽略]
```

- **结论**：复用收件箱已有的"最后一句可读总结"逻辑（`summarizeActivity` + `sessionQuery`），只读、不激活 Agent。每个条目只保留最新一条。
- **建议**：只从"先探索"的回复里解析 `next-steps` 代码块，最多 8 条。接受后变成普通待办，进入时间线；忽略后不再出现。Agent 没按格式输出时就没有建议，**不用模型去猜**。
- **完成提示**：goal 完成或你验收了 review 之后，条目显示「看起来完成了？[标记完成]」。只提示，不自动勾选，因为是否真的完成只有你能判断。

### 1.5 排：两条泳道的时间线

条目分成两类，消耗的东西不同：

| 泳道 | 哪些条目 | 消耗你的时间 |
|---|---|---|
| **我** | 没有关联、也没标记交给 Agent 的条目 | 估时（默认 30m） |
| **Agent** | 已关联 Session，或标记了「交给 Agent」 | 只算验收成本（默认 15m），另外受 **Agent 并发上限**（默认 2）约束 |

所以"今天 4 小时"能容纳的是：你亲手做的事，加上验收 Agent 结果的时间。Agent 的执行时间不挤占你的时间，只受并发上限约束。

```
┌──────────────────────────────────────────────────────────────────┐
│ 今天 11月25日 周三       你 ██████░░ 3h/4h    Agent ●●○ 2/3 并发 │
│  等你   ◑ 大纲笔记插件设计            验收 15m                    │
│  在跑   ◌ CI 环境变量迁移                                         │
│  待派   ○ 探索：loro-repo 接入        09:30 自动派出  [现在派]    │
│  我做   ○ 写周报 30m   顺延 2 次                                  │
│ 明天 11月26日 周四       你 ██░░░░░░ 1h/4h    Agent 1 待派        │
│ …                                                                 │
│ 稍后  ○ 研究 E2EE 半天   ⚠ 已拖 4 次 —— [拆分] [先探索] [放弃]    │
└──────────────────────────────────────────────────────────────────┘
```

**排程规则**（纯函数、确定性、每次读取时现算，只保存你手动做的选择）：

1. 固定项先放：手动日期 > 文字里的日期（今天/明天/周五/11月28日/@2026-11-28）。逾期的放到今天，并累计顺延次数。
2. 其余按 截止早 → 优先级高（`!`/`!!`/紧急）→ 创建早 排序，放进截止前最早一个放得下的日子。Agent 泳道还要满足当天并发不超限。
3. 截止前放不下 → 硬放到截止日并标"超载"；没有截止 → 进「稍后」。
4. **顺延 ≥ 3 次**的条目会给出三个选择：拆分（加子条目）、先探索、放弃。放弃不等于删除，会标记为"已放弃"并计入回顾。

**自动派发**（v1.1，默认关）：Agent 泳道里排在今天、标了「自动派出」的条目，到设定时间（默认 09:30）由 Host 依次开 Session，并发不超过上限，每天最多 N 个（默认 3）。放在 Host 做，浏览器不开也能跑；这需要先做 spike（见第 5 节）。

### 1.6 回顾：每天一份真实小结

每天第一次打开时，昨天的分组顶部生成一行小结（只用笔记和账本里的事实，不调用模型）：

> 昨天：完成 5 · 派出 3 个 Session（2 个已验收） · 顺延 2 · 放弃 1 · 收件箱原地处理 7

页脚是一段时间的指标（没有样本就显示无数据）：想法转化率（转成 Session 或完成的比例）、从记下到开始的中位时长、从开始到完成的中位时长、平均顺延次数。这些数字回答一个问题：**这套东西有没有让想法更快落地**。

## 2. 数据

新 storage domain `attention_notes`，和收件箱的 `attention_inbox` 分开：不改已发布的 schema，删掉笔记数据不影响账本。

```ts
interface Note {
  id: string; day: string; parentId: string | null; order: number
  text: string                                   // ≤ 4000
  kind: 'note' | 'result' | 'suggestion'         // result/suggestion 由 Host 写，只读
  state: 'open' | 'done' | 'dropped'; closedAt?: string
  createdAt: string; updatedAt: string
  sessionId?: string; mode?: 'task' | 'explore'; linkedAt?: string; workspaceId?: string
  plan?: { date?: string | 'later'; estimateMin?: number; lane?: 'me' | 'agent'; autoStart?: boolean }
  rollovers?: number                             // 跨日顺延次数，排程时累加
}
interface NoteSettings {
  capacityMin: 240; reviewCostMin: 15; agentConcurrency: 2; horizonDays: 7; skipWeekends: false
  workspaceId: null
  autoExplore: false; autoDispatch: false; dispatchAt: '09:30'; dailyAgentCap: 3
}
```

派生、不持久化的：时间线、状态、回顾数字。

路由 `POST /api/attention-notes`：`state`、`upsert`、`delete`、`link`/`unlink`、`accept`/`dismiss`（建议）、`settings`。每个 op 都返回完整状态；Client 做乐观更新，请求串行发送，打字 400ms 防抖保存。

## 3. 和收件箱的关系

- **共享**：Session 状态和原地处理复用收件箱的义务视图；同一个 Host 插件、同一个生命周期；结论回写复用 activity 摘要。
- **不共享**：存储、路由、徽标。笔记的侧栏图标不显示数字，保持默认安静。
- **可选**（v1.1，默认关）：今天排了但到下午还没开始的"我"泳道条目，作为一条 soft 义务进收件箱。

## 4. 范围与分期

| 版本 | 内容 | 理由 |
|---|---|---|
| **v1** | 大纲笔记、转对话/先探索、状态图标与状态条、结论回写、探索建议、两泳道时间线（只排不派）、顺延提醒、每日回顾、右侧栏 pin | 闭环的最小完整形态；只用已经确认存在的 API |
| v1.1 | Host 侧自动派发、自动探索、收件箱联动、从收件箱「记一笔」 | 会自动花钱或开 Session，需要先做 spike 和成本保护 |
| 以后 | 全局快捷捕获、从对话消息存为笔记、周报导出 | 依赖尚未确认的 Slot/快捷键接口 |

明确不做：富文本、日历同步、团队共享、精确到分钟的日程、用模型猜测"是否完成"。

## 5. 风险与待验证（spike）

| # | 问题 | 怎么验证 | 失败时的退路 |
|---|---|---|---|
| N1 | Host `sessionController.createSession` + `prompt` 能否在没有浏览器时开 Session 并发出 prompt，消息来源如何记录 | 隔离 DSH 环境实测 | 自动派发只在浏览器打开时由 Client 执行 |
| N2 | 一轮结束后，结论能否只读拿到且不激活 Agent | 复用 `refreshActivities` 路径做冷/热 Session 测试 | 只显示状态，不回写结论 |
| N3 | 右侧栏 tab 能否拿到"当前 Session"，用来挂靠新笔记 | `sidebarRight.mounted` 实测 | 右侧栏里的笔记统一记到今天 |
| N4 | `connectWorkspace` 并发复用同一个空白 Session | ~~串行化 + 测试覆盖~~ 复审发现它还会占用用户自己的空白会话 | 已改用 `sessions.create({ workspaceId })` |
| N5 | 成本失控 | 自动类功能默认关闭 + 每日上限 + 设置页显示今日已用额度 | — |
